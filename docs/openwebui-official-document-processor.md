# Open WebUI 公文 PDF／Word／ODT／圖片批次處理

`openwebui/functions/official_document_processor_pipe.py` **v3.13.0** 支援目前登入者在同一則訊息混合附加 PDF、ODT、DOC、DOCX，處理為依文號拆分／改名的 PDF、可編輯版面 DOCX，以及需要時的彙整行事曆 CSV。不另輸出可搜尋 OCR PDF。

它只把附件當成待分析資料；附件中的文字、連結、指令或 JSON 範例不會被當成系統指令執行。

## 單一路徑設計

每份文件只走一條固定流程，沒有 direct-PDF 雲端視覺、本機欄位正則解析、Tesseract、`pdf2docx`、影像 DOCX 或文字 DOCX 的替代路徑：

1. 驗證目前登入者對附件的存取權。可混合上傳 PDF、ODT、DOC、DOCX，**四種格式合計最多 10 個檔案**。或上傳 1–10 張屬於**同一份公文**的圖片；圖片與文件請分批。
2. Word／ODT 先使用既有 `office_input.to_pdf()` 隔離轉換器產生暫存 PDF；原始檔與其權限、檔案 ID 保留。接著所有 PDF 比對跨檔相同頁面，只讀取不同頁面的原文，以內文的本件發文字號分組，再建立附件及轉函關係。單份合併 PDF 也會識別其中各件函文；不同文號分別保留自己的欄位，只有明確相關的函文及附件能互補判讀。回覆按文號組列出下載，不另顯示原始來源清單。同一份公文的多張圖片依檔名自然排序、EXIF 旋轉與白色背景處理後合成一份暫存 PDF，沿用圖片組判讀。
3. 完全有原生文字層的 PDF 使用 `pdftotext -raw`。只要任一頁沒有原生文字，整份文件就使用 PaddleOCR-VL 的版面區塊文字；不混合可能不完整的兩種來源。OCR 區塊內的純視覺折行會保留為可供模型理解的連續內容，頁面與區塊邊界仍會保留。
4. `cloud_ocr_text_model`（預設 `gemini-3.8-flash`、`low` 思考等級）以**同一次整批請求**完成文號分組、附件關聯、正式名稱及各函欄位與事件判讀。來源文字只列一次，以固定來源 ID 與原始行號對應結果；程式先驗證分組，再依各函允許的正文／附件範圍核對欄位與事件，不把模型分組當成證據。需要匯出行程時，保留既有獨立語意核對及必要更正；超長來源仍須分段索引，故這兩種情況可能有額外請求。模型不收到 PDF／圖片位元組。
5. 原生文字 PDF 使用原生文字與座標建立可編輯 DOCX；掃描／混合 PDF 另外使用 PaddleOCR-VL `spotting` 逐行座標辨識。同一批各組共用已取得的頁面座標，按各自 PDF 頁序組合 Word，不為同一張共用附表逐組重做定位 OCR。語意文字 OCR 與 Word 定位 OCR 仍是不同用途的兩次處理；啟用快取時可跨次重用同一使用者的 OCR 結果。Word 轉檔結果在同批重用，重跑時重新建立下載。版面輸出失敗不取消其他已驗證的行程。
6. 每個文號組的主文與各份直接引用的無文號附件分開輸出 PDF 與對應 Word；多頁附表與其照片保留在同一份附件。同一附件被多份公文引用時，為各母公文分別命名及建立下載；相同頁面的 PDF 拆分、Word 轉檔結果在同一批內重用。同時上傳獨立檔與合併版時，相同頁面去重後再拆分。只有輸出恰好等於一份完整來源 PDF（Office 為轉換後 PDF）時沿用該 PDF 位元組，其餘使用原始 PDF 頁面組合，不重繪為圖片。所有原始上傳檔保留。

通過整批附件權限、大小及頁數檢查後，圖片／圖面附件只要能讀取相關文字，就能與主文互補，不必各自具備發文日期、文號與主旨。純圖形的空間關係目前不由文字 OCR 推定。

引用文號不等於已上傳的函件。關聯判讀只使用本批實際存在的其他公文組，去除重複及自身文號；
模型列出未上傳的引用函時，不中止本函處理、不新增公文組或假附件。原文中的引用仍完整保留。
實際附件函的下載連結仍須對應本批另一組函件，並通過母函引用證據驗證。這項處理不增加模型請求。

若某組有附件無法讀取，該組行程列為待確認，不以缺漏資料當作完整判讀；其他組繼續。取得分組後，單組欄位或行程驗證失敗不阻擋其他組。整批單次請求逾時或受限時，因尚無已驗證分組，不猜測拆分或文號，保留原始上傳檔，亦不另發逐組請求重跑。PDF／Word 輸出逐檔進行，Word 失敗時已產生的 PDF 及已通過驗證的行程保留。各組通過來源驗證與語意核對的行程，以及以這些日期為基準的 AI 建議準備提醒，共同建立一份 CSV；沒有可確認日期就不建立空白 CSV。失敗項目不在本批反覆重送。

公文欄位驗證與行事曆驗證／核對分開保存；若初次行程驗證失敗，或後續核對、修正遇到 429，已確認的日期、文號及主旨仍可用於正式改名，僅該組行程暫不納入 CSV。未能完成首次欄位判讀時才使用待確認檔名。

分組正式主旨直接採用 `document.evidence.subject` 的完整引文，經本件主文逐字驗證後才輸出，
不採用模型另抄一份的主旨。v3.12.3 由模型依語境選取內容，不以固定欄名裁切引文；
程式只整理排版折行並核對來源，不做關鍵字替換、近似比對或同音字更正。
引文不屬於本件主文時仍不能通過驗證，但該組 PDF／Word 可用待確認檔名輸出，其他組繼續。
這項修正不新增模型請求；缺少實際辦理日期時仍不猜填 CSV 或 AI 準備提醒。

分組及共同判讀只省略空白行與系統插入的 OCR 開閉標記，並以緊湊 JSON 傳輸；全部正文、頁碼標記及原始行號保留。行號间隔保留段落／區塊邊界，證據驗證與 Word 仍使用完整來源，不以摘要替代原文。

## 重跑快取

`document_analysis_cache_enabled` 預設開啟。沿用既有 PostgreSQL `processing_chunks` 與使用者隔離加密，
不新增資料庫或另存雲端對話。查詢前仍驗證目前登入者的檔案存取權；新上傳 ID 不影響重用，
輸出檔的來源及權限則重新綁定本次上傳。

- 快取鍵包含文件內容雜湊、檔名／順序、處理設定、模型請求的提示詞及 schema，以及流程快取版本。
  改檔、改名、改模型／思考等級／設定，或提示詞與 schema 改變時重新判讀。
- 啟用 AI 準備提醒時，台北當日日期也是提示詞的一部分；跨日重新判斷，避免沿用過時提醒。
- 相同使用者同時提交相同批次時，以 PostgreSQL advisory lock 等候先前處理，完成後再讀快取。
  不同使用者互不共用；取消請求會釋放鎖。
- 雲端失敗、分組無效、欄位原文證據不符或附件未讀完，不保存為可重用判讀。
  已驗證的公文欄位可保留，即使行程仍待確認；失敗的行程修正／核對回覆不保存。
  每次命中快取仍完整執行原文、附件及行程驗證，待確認項目不會因此變成已確認。
- 重跑會重建本次 PDF／Word／CSV 下載，不重用其他對話的檔案 ID，也不自動寫入 EIP。
  快取只省略相同模型請求及 OCR；本機驗證、拆分、Word 輸出仍會執行。
- 管理員若需要重新取得模型判讀，可暫時關閉此設定。更新驗證規則時應同步更新
  `processing_cache.UPLOAD_CACHE_REVISION`，使舊版本結果失效。

驗證：六頁範例的首次分組與判讀由 2 次降為 1 次，輸入 token 由 17,026 降為 14,157；
重跑快取測試不再呼叫 Gemini。仍輸出 3 組公文、8 PDF 與 8 Word，缺少明確日期的項目仍不產生 CSV。


## 輸出內容

每份成功文件會輸出：

- 改名／拆分 PDF：`{民國年月日}_{發文字號}_{主旨}.pdf`。主旨來自已驗證的逐字原文；雲端模型同次選出可獨立閱讀的來源原文短語供檔名受限時使用，不會改變 CSV 的正式主旨。若仍超過檔案系統安全長度，會在 Unicode 句讀／空白邊界截短並加上 `…`，不會假裝被截斷片語是完整句。
- 獨立附件 PDF：`{民國年月日}_{母公文文號}_附件1(附件名稱)-{主旨}.pdf`。附件順序依本件附件清單排列；名稱由既有分組判讀根據內容取得，未知時省略括號。不為附件命名新增模型請求。被多組引用的同一完整附件，各組依自己的日期、文號、附件序號、附件名稱與主旨命名；不再使用 `共用附件` 檔名或共用下載 ID。這些檔名表示附件隸屬哪份母公文，不是把母公文文號當作附件自身文號。
- 可編輯版面 DOCX：`{民國年月日}_{發文字號}_{主旨}.docx`。每頁以原始頁面作固定底圖，將 OCR 辨識出的中性文字行寫為同座標的一般 Word 文字，統一使用標楷體（`DFKai-SB`）。正文可選取與編輯；章戳、紅線、簽名及不能安全替換的彩色內容保留在底圖，因此不一定可逐字編輯。改寫過長的單一行仍可能在該行框內換行，匯出後應校對。
- 行事曆 CSV：單份命名為 `{民國年月日}_{發文字號}.csv`。只有至少一個通過來源驗證的期限、日期區間或明確時間事件時才建立。一批多 PDF 只會產生一份 `公文批次_{組數}組_行事曆.csv`；主文及不同附件各自輸出 PDF 與 DOCX。

依文號分組後，每組主文以自己的發文日期、文號及主旨命名；獨立函文即使被轉送也保留自己的組。無文號附件另外下載；相同完整附件只拆分及轉檔一次，但按各母公文建立各自的下載檔案與歸屬中繼資料。這會增加儲存副本，不增加同一批內的附件 OCR、判讀或 Word 轉檔次數。PDF／DOCX 共用檔名主體，包含副檔名不超過 200 UTF-8 bytes；原檔名不拼入新檔名。

若判讀遇到 429、逾時或無法確認改名欄位，仍使用分組時已核對的文號，暫名為 `{文號}_日期主旨待確認.pdf`／`.docx`；不猜填日期或主旨。已確認的文件欄位不受後續行事曆驗證失敗影響。來源頁面、重複頁的原始檔案 ID 與轉函關係保存在檔案中繼資料，不列在聊天回覆。未讀附件的頁面歸屬無法確認時，另外保留下載。

CSV 的 `Description`：文件有「說明」正文時，完整保留所有項次、子項、段落與跨頁續文，不以事件摘要取代；原有日期、附件引用與聯絡資訊也保留。沒有說明正文時，維持由模型閱讀全文後產生來源可驗證的內容說明。辨識仍依據 OCR／原生文字及雲端判讀。

不會建立全文 TXT、OCR 回應、模型回覆或未改字型的 DOCX 備份；這些資料只在單次請求記憶體中使用。

### Office 混合上傳（v3.12.0）

沿用 `ai-gateway/eip-office:1` 的 LibreOffice Writer 轉換器，支援 DOCX、
Word 97 二進位 DOC／既有 RTF 型 DOC，以及 OpenDocument Text（ODT）。
轉換在無網路容器內執行，禁用巨集，不改用主機的 Office 程式。
需要該映像已安裝；建置方式為 `docker build -f infra/Dockerfile.eip-office -t ai-gateway/eip-office:1 .`。
所有來源均先驗證登入者存取權；暫存 PDF 在完成、失敗或取消後清除，原始 Office 檔案保留。

轉換後的 PDF 若有完整文字層，直接取文字與座標；包含掃描頁時仍走既有 OCR。
不為了增加格式另發模型請求。分頁與字型依 LibreOffice 渲染，輸出 Word 仍為既有可編輯版面，
不是直接改名原始 DOCX。主文分組、附件依母公文命名、共用內容只轉檔一次、CSV 與 AI 準備提醒均保留。

驗證：10 個混合上傳項目（DOCX／DOC／ODT 各 3 個副本，加 1 個 PDF）實測通過。
原始 10 頁去除相同副本後判讀 3 頁，輸出 4 PDF、4 Word、1 CSV；兩筆原定行程及兩筆建議準備提醒。
Word 實際轉檔 3 次，沒有掃描座標 OCR，未修改原檔或寫入 EIP。
查看[混合格式實測輸出](../example_files/Office混合上傳測試結果/README.md)。
相關測試 281 項通過、18 項依原有條件略過；完整架構檢查另有 4 項既有失敗
（模組層級 import、無自訂例外包裝、無巢狀函式、無 try），已用修改前程式重現，未為本功能改動這些規則。

## Open WebUI 使用方式

1. 管理員在 **Admin Panel → Functions** 啟用 Function。
2. 使用者在新對話選擇：

   ```text
   公文 PDF／Word／ODT／圖片批次：附件拆分、可編輯 DOCX 與行事曆 CSV（雲端 LLM）
   ```

3. 一次選取或拖曳最多 10 個 PDF／ODT／DOC／DOCX，可混合格式。也可另批上傳同一份公文的多張圖片。多張圖片請以頁碼命名，例如 `001.jpg`、`002.jpg`、`010.jpg`；處理順序以檔名為準，不依上傳順序。
4. 上傳附件後送出訊息即可；例如「處理這些公文」或「滿難的」都會直接執行相同轉檔。回覆只提供 PDF、Word、CSV 下載及必要的失敗／無行程說明，不要求另寫操作指令。

同一聊天室後續新上傳的附件會重新以該次附件建立獨立處理工作；先前文件不會被拿來當作新文件的 OCR 或雲端判讀來源。

### 聊天入口固定輸出（v3.11.6）

此專用模型固定使用三種輸出設定，附帶聊天文字不送至工作指令規劃器，不因閒聊、空文字或模糊敘述阻擋文件處理，也不依文字省略 Word、追加自訂提醒或授權 EIP 寫入。v3.11.23 起，聊天 PDF 的事前準備提醒依文件內容自動建議，受下列獨立設定控制。

- 多份 PDF 去除重複頁後共同判讀，每組文號的主文與附件分開輸出 PDF／Word，相同附件共用轉檔結果、按各母公文分別命名儲存；通過來源驗證及語意核對的行程彙整為一份 CSV。
- 沒有可確認事件時保留 PDF／Word 並說明沒有 CSV，不捏造日期。
- 部分失敗會保留成功下載並說明失敗來源。
- 聊天入口不提供提醒釐清續接或 EIP 匯入連結；需要公文指令與匯入時使用 EIP 工作台。
- 變更限於 `Pipe.pipe()` 的聊天入口與回覆；EIP 的 `integration.process()`／`process_with_team()` 及 Company Agent 的 `billed_pipe()` 不經過此聊天入口，保留各自規劃、計費與確認流程。

## CSV 格式與資料規則

### AI 事前準備提醒（v3.12.1）

聊天 PDF／ODT／DOC／DOCX 批次預設啟用 `calendar_ai_preparation_reminders=true`。AI 在原有共同判讀請求中，
依主文及相關附件為每個有日期的待辦／活動提出 0–3 個準備步驟，通常 1–2 個；
自行選擇提前 1–7 個曆日，列出應準備的文件、圖說、資料或具體行動，以及安排理由。
每項依工作內容建議同一天的開始／結束時間（台北時間），並說明時長考量；優先選合理日間時段，
同日步驟避免重疊，不統一套用固定的一小時。這是建議排程，沒有讀取個人的行事曆空檔。
不另外呼叫工作指令規劃器或為了提醒重讀／重送整批文件，但新增 schema、提示詞與建議內容會增加 tokens。

原定行程須先通過既有來源驗證及語意核對，程式再從其期限日／活動開始日減去天數。
準備提醒是獨立的非全天 CSV 列，名稱以「準備提醒：」開頭並保留 AI 標記，說明明載
「AI 建議準備提醒（非公文明訂期限）」、準備事項、原定行程與日期、提前天數、建議時段、工時、安排理由及公文內容。
姓名固定「AI填寫」；兩種時間欄位均填入，工時從起訖時間計算，回報狀況填「待辦」、完成度填 `0`。
保留文號、發文日期、受文者、承辦單位及可靠的工程分類；受文者／承辦單位未載明時填「未載明」，
責任單位／受辦對象填「待指派（AI建議）」，不直接繼承原行程的責任人。
工程分類仍限既有可用分類，無法對應時留白。原公文行程的姓名、時間與其他來源欄位不受影響。

日期尚未確認、語意核對未通過、附件未讀取，均不建立準備提醒。
提醒早於台北當天或發文日就略過並說明，不移到另一個猜測日期。
模型輸出契約要求完整的 `HH:MM` 起訖時間；投影 CSV 時再次檢查時段，結束不晚於開始時僅略過該提醒，保留原定行程。
相同日期、工程、基準時刻及完全相同準備行動的建議會去重；不同建議不做模糊合併。
提醒不會再被拿來產生下一層提醒。原定事件即使已過去仍依既有規則保留。

## 安全、隱私與費用

- 雲端只收到完整的原生 PDF 文字或 PaddleOCR-VL 版面文字，不會收到原始 PDF／圖片位元組；文字仍可能包含敏感內容，僅應上傳組織允許送往該服務的文件。
- Pipe 只使用環境變數中的專用 loopback LiteLLM virtual key，絕不回退使用 `OPENAI_API_KEYS`、LiteLLM master key 或 Azure provider key。
- 請求不帶 OpenAI `user`、OIDC subject、email 或使用者名稱，且帶 `store=false`；不會扣除登入者的 LiteLLM 個別每日額度。實際雲端成本仍記在專用服務 key。
- 聊天 PDF 的主要模型請求為一次分組與一次整批判讀；超長來源分段索引、必要的行程語意核對／更正會增加請求，不能保證所有批次都恰好兩次。圖片組沿用單件流程。聊天文字不呼叫工作指令規劃器；需要選擇多個期限時，另發只含使用者回答與已驗證日期清單的短請求。OCR 循序處理，共用附件的文字座標在同一批內重用。
- Pipe 不會在日誌或衍生檔 metadata 寫入 PDF 位元組、全文、OCR 區塊／座標、原始模型回覆或 virtual key。Open WebUI 仍依自身設定保存原附件與使用者可下載的衍生檔。

## Lite 與原生結構化輸出（v3.11.16）

公文流程經 LiteLLM `/v1/responses` 呼叫 Vertex Gemini，沒有直連 GCP 的另一條路徑。Responses 的外層格式與模型產生的業務 JSON 是不同層次：`json_object` 只要求合法 JSON，不指定必填欄位或型別；`json_schema` 才將應用程式的資料契約交給供應商約束。[LiteLLM 官方文件](https://docs.litellm.ai/docs/completion/json_mode) 說明兩者差異及 Gemini 原生 schema 支援。

分組、公文分析、單件判讀、行事曆核對及長文證據索引的契約，使用 Pydantic 產生 JSON Schema，透過 Gemini 請求的 `text.format` 傳入。日期值與逐字日期證據使用不同欄位說明：前者轉成西元，後者必須保留原文。既有其他供應商仍使用原本的 JSON 模式。正式回答只讀取 Responses 的 `message`／`output_text`，不把 `reasoning` 內容併入待解析 JSON；欄位來源與日期正確性仍由既有驗證負責。

預設改為目前已設定的 Gemini 系列中最低階的 `gemini-3.5-flash-lite`、`low`，輸出上限維持 3,000。197 項測試通過，另完成下列真實 Lite 請求：

- 六份使用者 PDF：重用本次診斷取得的完整 OCR，正確分為一組，正式改名並實際產出六份 PDF、六份版面 DOCX。PDF 與來源逐位元組相同，DOCX 可開啟，沒有待確認檔名。部分行程缺少確定日期，仍未產生 CSV。
- 四份虛構混合公文：正確分為兩組，從不同附件補齊日期、會勘起訖時間，通過語意核對並匯出兩筆 CSV 行程；該案例的 OCR／儲存使用替身。
- 單件判讀：實際主文的日期、文號與檔名通過來源驗證；另一份有明確期限的測試文件擷取出一筆期限。

## 同檔多公文自動拆分（v3.11.18）

若單一上傳 PDF 的內文包含多個不同本件文號，沿用已辨識的各公文正文與無文號附件頁，為每個公文組另存 PDF，並由同一份拆分 PDF 產生 Word。只有明確相關的附件頁能一起輸出，其他函文正文不混入；共用附件可出現在多組拆分結果。單件公文的 PDF 沿用原始位元組；原始上傳檔不覆寫或刪除。

拆分直接使用 [PyMuPDF `Document.select`](https://pymupdf.readthedocs.io/en/latest/document.html#Document.select) 與另存新檔。伺服器記錄拆分结果對應的原始頁碼與上傳檔案 ID，以維持來源權限及追溯；聊天仍不列原始來源清單。辨識與分組不因拆分增加雲端模型請求。

原生文字與 OCR 的頁面標記保留空白頁及實際頁碼，不把第三頁誤編成第二頁。不同公文的正文若被標在同一個實體頁面，會要求確認，不能假裝整頁拆分已分開兩件內容。

## 各公文的直接附件歸屬（v3.11.19）

移除跨組共用輸出快取，各組的共用附表依自己的日期、文號與主旨命名，避免第二組顯示第一組的檔名。合併 PDF 依各組正文及直接附件頁拆分，PDF 與 Word 使用相同頁面，先放主文，再放附件；各部分維持原始相對順序。

## Open WebUI 輔助任務不重跑公文（v3.11.22）

Open WebUI 的搜尋詞、標題、標籤及追問生成會以同一模型呼叫 Pipe，並可能繼承本次附件。入口使用官方 `__task__` 參數區分輔助任務；只在正常聊天請求時進入文件流程。輔助任務回傳對應空 JSON 結果，不讀取附件、不呼叫 OCR／LLM、不產生文件，也不清除待確認行程。空標題由 Open WebUI 原生邏輯改用首則訊息；未知的輔助任務同樣不執行文件工作。

這處理的是平台自動觸發的重複流程。使用者主動重新產生或另送一次附件，仍會建立新的一輪文件處理；一次正式流程可以包含分組、公文判讀及行事曆核對等多次模型請求。

官方契約：[Reserved Arguments — `__task__`](https://docs.openwebui.com/features/extensibility/plugin/development/reserved-args/#__task__)。

驗證：127 項公文流程回歸測試通過，包含帶附件的 12 種輔助任務及正式請求與輔助任務並行時只產生一套輸出。以本機安裝的 Open WebUI 真實 Function dispatcher 對照舊／新版，確認舊版輔助任務進入檔案處理、新版略過，正常聊天仍執行一次。部署並重啟後，正式服務的 title／tags／follow_up／queries 四個 API 均回應 200 與正確 JSON；沒有新增公文模型請求或檔案。
