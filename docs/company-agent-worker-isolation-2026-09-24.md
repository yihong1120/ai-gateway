# Company Agent 單次工作失敗隔離

## 原因

2026-09-24 00:12:41 的模型請求收到 Vertex AI HTTP 429。原本 `Service.loop()` 直接等待工作執行，例外會終止唯一的背景 worker。後續 `service()` 與聊天輪詢呼叫已失敗 worker 的 `task.result()`，因此新工作也會收到舊例外，未再呼叫模型。

這不是公文處理結果快取；清除文件判讀快取無法修復背景 worker。

## 修改

- 僅在工作佇列的執行邊界隔離單次工作例外，記錄該筆佇列狀態為 `error`，然後繼續領取下一筆工作。模型與工具函式仍拋出原生例外。
- 當前程序保留按使用者及工作 ID 區分的原生例外。聊天輪詢與單筆工作查詢先驗證所有權，再回報該工作自己的例外；列表與其他工作的下載不受影響。
- 例外移除舊 traceback，避免持有或由呼叫端清理仍在運行的 worker frame；保留例外類別、訊息及 HTTP 狀態。
- 重啟時先取得既有 PostgreSQL 單一 worker 鎖，再將無執行者的 `running` 工作改為 `interrupted`。保留 checkpoint、來源與成果，不自動重播可能已完成的外部操作。
- 取消與服務關閉仍原樣傳遞 `CancelledError`，釋放 worker 鎖；未領取的工作保持排隊。

沒有修改模型、重試、備援或公文判讀快取。這項修改修復舊例外阻塞新工作的問題；新的上游 429 仍會回報給實際收到該錯誤的工作。

原生例外僅保存在當前程序，未將供應商錯誤內容寫入共用工作列表。服務重啟後仍可查看工作終止狀態及既有檔案，但不重新建立舊 Python 例外物件。

## 驗證

在每個測試獨立的 PostgreSQL schema 執行 112 項測試，全數通過，涵蓋佇列、聊天上下文、Pipe、模型路由與計費、HTTP 權限、例外邊界及 LangGraph checkpoint。

新增回歸情境：

1. 第一筆模型請求回傳 429，隨後同使用者的新工作及另一位使用者的工作都正常完成；只有三次模型請求，沒有重送失敗請求。
2. 只有失敗工作的本人取得原生 429；工作列表、其他工作與下載正常，未洩露其他人的例外。
3. 重新啟動不重跑舊的 `running` 工作，保留其成果並執行真正排隊的新工作。
4. 執行途中取消 worker，會取消當前工作並釋放鎖，不誤領下一筆。
