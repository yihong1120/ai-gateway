# EIP 每小時自動處理：覆蓋設計與驗收

## 結論

本輪針對 `/eip` 的每小時 pipeline，不是聊天 `company_agent`。
已修正兩類流程缺口並新增 16 項測試。離線／隔離回歸通過，但**未達全面上線放行**：
8 件真實文件全部執行，固定獨立驗收通過 5 件，3 件仍未通過。
沒有刪除處理紀錄、重建正式行程、修改分享對象、上傳正式附件或重啟服務。

依 [OpenAI 評測原則](https://developers.openai.com/api/docs/guides/evaluation-best-practices)，
分開評估工作流程、語意正確性及外部服務；使用固定標準、故障注入、真實文件與獨立評分。
模型的核對批准不當作正確答案；失敗不刪除、不改預期值換取通過。
本輪沒有修改生產提示詞，也沒有把案例名稱、日期或答案寫入提示詞。

## 已實作修正

### 附件先檢查，行程後新增

舊路徑先建立行程、再讀取附件；附件遺失或權限不符會留下缺附件的行程。
新路徑先對所有待新增群組讀取本人擁有的改名原始 PDF，再進行行程新增。
啟用夾檔卻沒有 PDF，現在明確停在待檢查，不再默默略過夾檔。
檔名與大小驗證也提前完成，與真正上傳端共用 `validate_upload`；不複製兩套限制。
超長或含路徑的檔名會在新增前退回；沒有任意放寬限制或更動原始下載檔名。
上傳仍在行程新增回讀成功後，沿用專案及分享對象的驗證結果。
既有 done 收據不會因本輪附件不可讀而要求重新上傳或重新新增。

新增前置檢查的兩個測試先在舊實作失敗，修正後通過；沒有移除原本去重或權限檢查。
這不是遠端交易：新增後若 EIP 上傳失敗，仍須保留收據並待核對，不能把整筆重新新增。

### CSV 補產的暫時故障可續跑

原本補產路徑把模型 `deferred` 當成一般失敗，可能永久停在待檢查。
現在回傳 `EIPRetryableError`，保留來源及 PDF／Word，至少一小時後只重做 CSV 分析。
同一輪已遇到暫時模型故障，後續補產與文件模型工作不再連續呼叫模型。
原文驗證失敗仍屬待檢查，不能誤標為限流，也不能自動放寬日期或責任要求。

## 尚需完成的設計與放行條件（未假稱已實作）

1. **責任語意是阻斷項**：針對執行者／收件者／交付對象的互換對照獨立驗收。
   下一輪應讓候選結構明確保留動作、執行者、對象及條件的關係，而不是只增加案例關鍵字。
   通過引文存在性或模型自評不能取代責任驗收；未修正 59161 前不得宣稱全面可靠。
2. **相對日期缺事實不能補猜**：明確區分「未知起算日」與「日期格式錯誤」。
   起算事實不存在時應保持待補，不用發文日、文件匣時間或今天代替。
3. **專案不存在是設定／授權問題**：需管理員建立或授權正確專案，或使用者明確選擇私人事項。
   不由 LLM 虛構 project ID，也不能為通過驗收任選其他工程。
4. **同來源同時段獨立工作**：現行去重會保留待核對，不直接匯入。
   若要支援，需引入有來源依據的穩定事件識別及更新／撤銷對帳；不能只以標題差異判為新事件。
5. **正式寫入驗收仍缺指定範圍**：使用指定測試帳號／專案，實際新增→回讀內容／時間／私人設定→
   專案／分享核對→上傳→下載附件核對雜湊→下一輪與重啟無重複。測試內容須明確標註，清理另依授權。
6. **部署前**備份日誌與獨立金鑰，確認資料庫 schema 初始化與版本；部署後驗證至少一次實際排程。
   不清除舊收據，不把 unknown 改成未處理，不重放所有待檢查。
