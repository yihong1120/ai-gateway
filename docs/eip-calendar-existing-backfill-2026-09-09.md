## 現場發現並修正

1. 三筆舊行程的更新回傳 HTTP 500，回讀證明尚未變更。連名稱單独更新也失敗，排除只有附件上傳造成錯誤的假設。
2. 三筆均有較長中文自訂欄位。舊程式將 CSV 匯入後儲存的原文再次轉成 `%uXXXX`，使欄位字串膨脹。改為原樣帶回既有自訂欄位後，使用相同已上傳附件完成三筆更新及回讀驗證；未重新上傳這些檔案。
3. 修正共用 `repair_parameters`：自訂欄位保留 EIP 儲存的表示方式，HTTP 表單層負責傳輸編碼；原為原文或已編碼值均不再改寫。未取得 EIP 伺服器錯誤日誌，故不宣稱已確認資料庫實際欄位長度限制。
4. 核對官方頁面 `cm_newevent.htm`、`attach.js`、`new_event.js`，既有附件詳細列的第 5 欄是 OID，不是站台 ID。補件保留原 OID，站台 ID 另從帳號的 `PerManDepList` 取得，避免既有附件遺失。

## 安全續作與驗收

- 上傳前先保存加密快照、來源檔案雜湊與寫入回執，逐筆比較新鮮的 EIP 詳細資料，變更衝突即停止該筆。
- 遇到錯誤不盲目重送；讀回確認後才做具體修正。已上傳但未綁定的檔案使用原識別碼續接。
- 真正更新後，再核對完整行程、分享對象、附件名稱／識別碼／大小與下載內容。
- 保留原 PDF、Word、舊 CSV；僅切換處理紀錄中的下載 CSV 引用，並新增同一 event_id 的去重別名。
- 加密操作快照與驗收結果存於 EIP connector 私有 `operator_backups` 目錄，檔案權限 0600；此公開驗收文件不含帳密、token 或完整公文內容。
