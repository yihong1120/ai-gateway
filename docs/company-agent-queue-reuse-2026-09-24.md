# Company Agent 重跑共用工作與排隊進度

## 問題

同一聊天室對同一問題按重新產生時，Open WebUI 會配置新的 assistant message ID。舊佇列只依這個 ID 去重，因此會建立三筆內容、附件與上下文完全相同的工作。

背景 worker 依序執行。原先第一筆已成功取得 EIP 行事曆的主旨與時間，但 Agent 又擴大到 NAS 搜尋、閱讀不相關檔案，耗用多輪模型呼叫；後兩筆一直排隊。第一筆與第三筆最終遇到 429，第二筆完成。這次並非 worker 被舊例外終止。

## 修改

- 同一使用者、計費身分、聊天室內，內容、附件、歷史來源及 NAS／EIP 綁定相同的排隊或執行中工作，重新產生會共用原工作。
- `request_aliases` 保存新的 assistant ID。後續聊天分支仍可找到共用工作的來源與成果，不會因重新產生而遺失引用。
- 登入身分、綁定、附件、上下文或聊天室不同，不共用。已完成、失敗或中斷後重新產生，仍可建立新的工作。
- 去重與建立工作共用原有 PostgreSQL transaction lock；不重複複製附件或新增模型任務。
- 真正排隊的不同工作會顯示前方工作數；同一進度不再每五秒新增相同狀態訊息。
- 行程細節查詢先依行事曆實際欄位回答。如果只有主旨與時間，明說尚未取得詳細議程；沒有具體文件線索或使用者的跨系統查詢要求時，不為補足細節擴大掃描 NAS。檢索角色也應在沒有新線索時交回限制，不原樣重查或 OCR 無關檔案。

跨系統查證與原有模型設定仍保留。不同工作依序排隊；這次未增加模型併發量。
